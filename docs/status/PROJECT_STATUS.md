Issues found and fixed during verification (each now covered by a test):

- Wildcard CORS origins (`https://*.example.com`) passed validation because URL parsing accepts `*` in hostnames → now rejected explicitly.
- Disallowed CORS origins still received `Access-Control-Allow-Credentials` → CORS now runs only for allowlisted origins.
- The first readiness check after startup reported a healthy Redis as down (offline queue disabled) → `ping` now waits, bounded, for the connection.
- DB-unavailable errors from the Prisma 7 driver adapter surfaced as 500 → mapped to 503 based on the adapter's real error shape.
- Access logs carried no request id, and recorded the proxy's IP instead of the client's → fixed (`quietReqLogger`, `req.ip`).
- nginx redirects used the container's internal port (broke behind port mapping) → `absolute_redirect off`.
- Zod's JIT capability probe violated the admin CSP (`script-src eval`) → Zod jitless mode in the browser.
- **First GitHub CI run:** type-aware lint failed on the clean runner (100 errors) because the Prisma client and `@nexora/shared` types are generated artifacts that did not exist yet; locally they masked the problem. Reproduced by deleting the artifacts, then fixed with a root `codegen` step that `lint`, `typecheck` and `test` all run first.
- A 393 MB deploy footprint was investigated: `prisma` moved to devDependencies and migrations got a separate `migrator` image target (the residual size is R-07).

### Node.js compatibility (follow-up)

A user on Node 23.7.0 could not install the project. Investigation on a real Node 23.7.0 binary found:
`engine-strict=true` turned dependencies' declared engines (many tools exclude odd releases on principle)
into hard errors; Prisma's `preinstall` script is a Node-version gate that rejects 23.x; and jsdom 30
(test-only) needs `zlib.createZstdDecompress`, which Node 23.7 lacks. Fixes: engines are now warnings
(the project's own range is `^22.22.0 || >=23.6.0`, checked by `nexora doctor`), Prisma's gate script no
longer runs (its engines still install via `@prisma/engines`), and jsdom is pinned to 29.1.1. On Node
23.7.0: fresh install, lint, format, typecheck, build, all unit/integration tests, drift check, the E2E
suite and `nexora dev` pass. CI now also runs the test suite on Node 23.7.0 and 24.

- **CI on GitHub:** run #1 (commit `d2b4f86`) passed the test job (unit, integration, drift check, E2E on 3 viewports), the audit, and all image builds; the lint job failed as described above. Run #2 (commit `57d5e1b`, with the fix) passed **all four jobs** on GitHub.

## Milestone 2 — Identity, access control and audit

Plan, scope and decisions: [`docs/milestones/m2-identity-access.md`](../milestones/m2-identity-access.md).

### Starting point
M1 delivered the API kernel, the `system_state` table and an admin shell with one public status page. No
authentication existed and every endpoint was public.

### What was built
- **Data model** (migration `20261031120000_identity_access_audit`): `sites`, `users`, `user_credentials`,
  `sessions`, `roles`, `capabilities`, `role_capabilities`, `role_assignments`, `password_reset_tokens`,
  `audit_events` (append-only trigger), `rate_limit_buckets`; CHECK constraints for normalised emails, key
  formats and hash lengths; 10 core capabilities and 6 system roles seeded by the migration.
- **Setup wizard**: environment check → site → security → first super administrator. It needs the one-time
  setup token (printed at startup, or `SETUP_TOKEN`); installation is serialised with a PostgreSQL advisory
  lock and permanently locked afterwards.
- **Sessions**: Argon2id passwords; opaque 256-bit session tokens with only their SHA-256 stored; cookie
  `__Host-nexora_session` (Secure) or `nexora_session` (plain-HTTP development), HttpOnly, SameSite=Strict;
  idle and absolute expiry; rotation on sign-in and password change; revocation of one session, all other
  sessions, or all of a user's sessions.
- **CSRF**: `Origin`/`Sec-Fetch-Site` verification on every unsafe request, plus a session-bound HMAC token
  (`X-CSRF-Token`) on every cookie-authenticated mutation.
- **Rate limits** (Redis when configured, PostgreSQL otherwise): sign-in per address and per account,
  password reset requests and confirmations, setup. Responses carry 429 + `Retry-After`.
- **Authorisation**: a global guard that denies by default; every route is `@Public`, `@Authenticated` or
  `@RequireCapabilities(...)`, enforced by a route-inventory test. Escalation rules live in one service: no
  granting of unheld capabilities, no self role/status change, no editing of more privileged users or of
  one's own role, the Super Administrator role is immutable, and the last active super administrator cannot
  be demoted or suspended.
- **Users, roles, account, settings, audit APIs** (24 OpenAPI paths), password reset by email (development
  transports only, see limitations) and operator recovery: `nexora user reset-password --email <email>`.
- **Admin UI**: setup wizard, sign-in, forgot/reset password, users (search, filters, pagination, create,
  edit, role, suspend/reactivate, set password, sessions), roles (custom roles, capability editor), audit log
  (filters, pagination), profile (name, password, own sessions), site settings; capability-aware navigation
  and routes; session-expiry handling; lazy-loaded routes.

Issues found and fixed during M2 verification:

- **Sign-out did not leave the page**: clearing the whole query cache detached the session observers, so the
  route guards never re-rendered → only the session entry is replaced and private queries are removed
  (covered by the admin auth-flow tests and E2E).
- **Route-level code splitting broke the CSP guarantee**: chunks containing shared schemas were evaluated
  before the entry's Zod jitless switch, so Zod probed for `eval` and the CSP reported a violation. Rolldown's
  `strictExecutionOrder` fixed it but cost ~6 kB of runtime wrappers; instead `src/zod-config.ts` is placed in
  Zod's own chunk, which every schema chunk imports (the E2E CSP test guards this).
- **Mobile layout**: row actions in the users table were pushed off-screen and toasts covered the header →
  role and status move under the name below the `sm` breakpoint; toasts sit bottom-right.
- **nginx forwarded `Host` without the port** (`$host`), so behind a mapped port the CSRF origin check would
  reject every sign-in through the container stack → `$http_host`.
- **Own password change had no automated test** (found while mapping the acceptance criteria to evidence) →

- **`nexora user reset-password` always failed**: pnpm 10 forwards a literal `--` to the script, which made

- **Initial admin bundle grew to ~225 kB gzip** with the M2 screens → routes are lazy-loaded (209.7 kB) and

### Known limitations and caveats (honest list)

- **No production mail delivery.** Transports are `log` and `file` (development/test only, refused in
  production) and `disabled`. In production a "forgot password" request is accepted but no email is sent;
  administrators can set passwords and operators can use `nexora user reset-password`. SMTP arrives with the
  job queue in M3 (R-11).
- **Reset emails are sent in-process** after the response; a crash before delivery loses the message (R-11).
- **Expired sessions and reset tokens are not purged yet** (they are rejected, just kept). Rate-limit buckets
  are purged opportunistically. A scheduled cleanup job arrives with the job queue (M3).
- **Not implemented:** email verification, MFA/2FA, SSO/OAuth, API tokens for non-browser clients.
- **Content capabilities do not exist yet**, so Editor, Author, Contributor and Viewer can only sign in and
  manage their own profile until M3.
- **Setup token in the log** when `SETUP_TOKEN` is unset (R-09). Per-account lockout can be triggered by
  anyone who knows an address (R-10).
- **Fixed-window rate limits** allow up to twice the limit across a window boundary.
- **Idle-timeout precision**: session activity is written at most once a minute, so idle expiry is accurate
  to about 60 seconds.
- **The production-like Compose stack serves plain HTTP on 127.0.0.1** with Secure cookies. Browsers accept
  Secure cookies on `localhost`/`127.0.0.1`, so it works locally, but any real deployment must terminate TLS
  in front of it; otherwise sign-in cookies are rejected.
- Local tests ran against PostgreSQL 16; CI and Compose use 17.
- **GitHub CI:** run #9 (commit `d4dce53`) passed all six jobs: lint/format/typecheck/build/bundle budget, unit + integration + drift + E2E, Node 23.7.0 and 24 compatibility, dependency audit, container images.

## Milestone 3 — Content, media and background jobs

Plan, scope and decisions: [`docs/milestones/m3-content-media-jobs.md`](../milestones/m3-content-media-jobs.md).

### Starting point
M2 delivered identity, sessions, capability-based authorisation and the audit log. Mail was sent in-process with
development transports only, expired security records were never purged, and the content roles could only sign in.

### What was built
- **Job queue** (`apps/api/src/modules/jobs`): PostgreSQL table, transactional enqueue with `NOTIFY`, claims with
  `FOR UPDATE SKIP LOCKED`, exponential backoff, `dead` after the last attempt, reclaim of abandoned claims,
  ownership-checked completion, dedupe keys, recurring tasks that run once per slot, graceful shutdown that releases
  unfinished work, worker heartbeats. Embedded in the API (`JOBS_WORKER=embedded`) or standalone (`dist/worker.js`).
- **Mail**: SMTP transport (TLS and certificate checks required in production); password-reset emails are produced
  by a job that creates the token at send time, so job payloads never contain it.
- **Maintenance**: hourly purge of expired sessions, reset tokens, rate-limit buckets, finished jobs and stale worker
  heartbeats; scheduled publishing every minute; trash purge hourly.
- **Content model**: content types (Post, Page, custom) with custom fields (text, long text, number, yes/no, date,
  choice, URL, email, media); taxonomies (Category, Tag, custom) and terms; entries with draft/pending/scheduled/
  published states, a separate trash, hierarchical paths, slugs, excerpts, featured images, a structured rich-text
  body, optimistic concurrency, revisions with restore, bulk actions, search and filters.
- **Content capabilities** (`content.*`, `terms.manage`, `content_types.manage`, `media.*`, `jobs.manage`) mapped
  to the built-in roles by the migration, and one content policy for own vs. others' entries and live content.
- **Media**: content-sniffed uploads, re-encoding without metadata, WebP variants via a job, local and S3 drivers,
  `/uploads` serving with safe headers and byte ranges, usage counts, ownership rules.
- **Admin**: content lists, the editor (TipTap rich text, scheduling, slug, excerpt, featured image, terms, custom
  fields, parent page, revisions, unsaved-changes guard, conflict handling), media library and picker, term
  management, content type and field builder, background jobs page, command palette; navigation generated from the
  content model.
- **Infrastructure**: Compose `worker` service and shared `media-data` volume; nginx routes `/uploads` and allows
  large bodies on the upload endpoint only; CI runs an S3-compatible server for the S3 driver tests.

## Milestone 4 — Public site, themes and Delivery API

Plan, scope and decisions: [`docs/milestones/m4-site-themes-delivery.md`](../milestones/m4-site-themes-delivery.md).

### Starting point
M3 delivered the content model, media and background jobs. Content could be published, but nothing rendered it for
visitors: `/` in the container topology returned 404 and there was no read API for published content.

### What was built
- **Delivery API** (`apps/api/src/modules/delivery`, public, read-only): resolves a path to a page — home (latest
  posts or a static page), entry, archive (content type or term), redirect or not found — together with the site
  data a theme needs (identity, language and direction, SEO defaults, resolved theme settings and media, menus);
  sitemap and feed data; preview pages. Every query uses one "publicly visible" predicate plus a path-based ancestor
  check; custom fields are delivered only when marked public.
- **URLs and redirects**: route prefixes for content types and taxonomies (posts `/blog/…`, pages at the root,
  `/category/…`, `/tag/…`, custom types under their prefix), reserved paths (`admin`, `api`, `uploads`) and
  collision checks (between prefixes and against root pages); automatic, flattened 301 redirects when a published
  entry's path, a term's slug or a prefix changes; manual redirects with source/target validation and loop
  detection.
- **Previews**: `POST /entries/{id}/preview` issues a one-hour link (256-bit token, only the SHA-256 stored); the
  site shows the latest saved version with a notice, `noindex`, `no-store` and no referrer.
- **Site settings and SEO**: general settings (name, tagline, language → text direction, home page, posts per page),
  SEO settings (title template, default description and social image, search engine visibility), per-entry SEO
  (title, description, `noindex`). New capabilities `appearance.manage` (administrator) and `seo.manage`
  (administrator, editor).
- **Themes**: `packages/theme-sdk` (types, safe rich-text and responsive image components, helpers) and
  `packages/theme-starter` (manifest with seven settings and two menu locations; React templates for home, entries,
  pages, archives, not found and previews; light/dark; logical CSS properties for right-to-left; Persian and English
  interface strings; no client-side JavaScript). The API validates theme settings against the manifest.
- **Menus**: menus with nested items (entry, term, home, custom link; up to three levels) assigned to theme
  locations; unpublished targets are left out of the delivered menu.
- **Site runtime** (`apps/site-runtime`): Express + React server rendering from the Delivery API only (no database,
  no credentials); the runtime writes the document head (title template, description, canonical, robots, Open
  Graph, Twitter, JSON-LD), `robots.txt`, `sitemap.xml` and RSS; CSP `default-src 'none'` with no script source and
  styles only from its own origin (theme variables are a re-validated stylesheet, not inline CSS); strong ETags and
  304s; 404 pages from the theme; 503 with `Retry-After` when the API is unreachable.
- **Admin**: dashboard (new start page), Appearance (site identity, reading, theme and generated theme settings
  form), Menus (tree editor), SEO and Redirects pages, an SEO panel plus View/Preview buttons in the editor, address
  prefix/visibility for content types and taxonomies, a "public" switch for custom fields, a "View site" link.
- **Infrastructure**: `site` image and Compose service; nginx routes everything outside `/admin/`, `/api/` and
  `/uploads/` to the site and keeps `/_preview/` out of the access log; `nexora dev` and the Vite dev/preview
  servers serve site, admin and API from one origin; CI builds the site image; Playwright runs against the site
  runtime.
- **Fixes found on the way**: partial updates of content types and terms reset omitted fields to their defaults
  (Zod `partial()` keeps defaults) — fixed with default-free update schemas and covered by tests; the built-in
  content types were listed in an arbitrary order (same creation time) — now fixed; a Redis dump file had been
  committed in M3 by accident — removed and ignored.

## Milestone 5 — Visual builder and shortcodes

Plan, scope and decisions: [`docs/milestones/m5-visual-builder.md`](../milestones/m5-visual-builder.md).

### Starting point
M4 rendered published content with the starter theme, but every entry was a single rich-text document: no way to
lay out a page (sections, columns, buttons and images side by side) and no way to place dynamic content (latest
posts, galleries) inside text.

### What was built
- **Builder documents** (`packages/shared/src/contracts/builder.ts`): typed, versioned JSON — sections (boxed or
  full width) → columns (width per breakpoint, vertical alignment) → widgets: heading, text (rich text), image,
  button, spacer, divider, video (YouTube/Vimeo privacy-enhanced), posts, shortcode, HTML embed. Every element has
  typed styles per breakpoint (spacing, colours, alignment, font size, radius, max width, min height, hide on
  device). One schema validates in the browser and the API with limits; `schemaVersion` with an upgrade function;
  newer versions refused.
- **CSS compiler**: `compileBuilderCss` turns typed values into rules scoped by element id, tablet/mobile
  overrides as container queries (each breakpoint inherits from the larger one); values are re-checked before they
  reach CSS.
- **Shortcodes** (`shortcodes.ts`): WordPress syntax `[name attr="value"]` in rich text (posts, pages) and builder
  text/shortcode widgets; registry of typed definitions — `button`, `recent_posts`, `gallery`, `video`,
  `site_name`, `year`; bounded linear parser; unknown or invalid shortcodes stay literal text and are flagged in the
  editor; `[[name]]` writes `[name]`. Dynamic shortcodes are resolved by the Delivery API; nothing is executed.
- **API**: `entries.editor` and `entries.builder` (migration with CHECK constraints), `content_types.has_builder`
  (on for pages); switching to the builder converts the rich-text body into a text widget (the body is kept);
  revisions and restore include builder documents; admin search covers builder text; new capability
  `content.embed_html` (administrator, editor) required to add or change HTML embeds; builder images must exist in
  the media library. Delivery API: compiled `builderCss`, resolved `shortcodes` and `posts` (public content only,
  at most 20 dynamic items per entry), embed code removed from page payloads and served by
  `GET /delivery/embed/{entryId}/{widgetId}` and the preview equivalent.
- **Theme SDK and starter theme**: React renderers for builder documents and shortcodes, `builder.css`
  (layout, buttons, video ratios, posts grid, gallery, responsive rules); builder pages render full width with the
  title aligned to boxed sections (or hidden by a page setting); block shortcodes inside paragraphs render without
  invalid markup.
- **Site runtime**: the page's builder CSS is sent inline and allowed by its SHA-256 in the CSP
  (`style-src 'self' 'sha256-…'`, no `unsafe-inline`, no nonce, so ETags stay stable); HTML embeds at
  `/_embed/{entryId}/{widgetId}` (and `/_preview/{token}/embed/{widgetId}`) with
  `Content-Security-Policy: sandbox allow-scripts allow-popups allow-forms` — an opaque origin.
- **Admin builder** (`apps/admin/src/features/builder`, lazy chunk of 29 kB gzip): full-screen editor with widget
  library, canvas rendered by the same components and CSS as the site, navigator, properties panel (content,
  per-device style form showing inherited values, page settings), drag and drop with `@dnd-kit` (from the library,
  between columns, sections by handle; pointer, touch and keyboard sensors; plus move up/down buttons), duplicate,
  delete, column count and widths, device preview (desktop/tablet/mobile), undo/redo (Ctrl+Z / Ctrl+Shift+Z; typing
  in one field merges into one step), unsaved-changes protection, save/publish with version checks, preview links.
  The entry editor links to the builder, content types get a "Visual builder" switch, and the revisions dialog
  summarises builder revisions.
- **OpenAPI**: large shared schemas are now hoisted into named components (`BuilderDocument`, `EntryDetail`,
  `DeliveryPage`, …) instead of being repeated per operation; the document shrank from 3.6 MB (with builder
  schemas inlined) to 0.36 MB, smaller than at M4 (0.69 MB).
- **Fixes found on the way**: adding a section from the canvas cleared the selection (the click reached the canvas
  background), so the next widget landed in the wrong section — found by E2E, fixed, covered by an RTL test; the
  canvas lost heading sizes and list markers to the admin's CSS reset — restored inside the canvas only; the admin
  image did not contain the theme SDK the builder now uses (the image build failed) — found by rebuilding the
  images, fixed in `admin.Dockerfile`; the revisions dialog showed the stale rich-text body for builder revisions —
  it now summarises the layout.

  theme's stylesheet (that would bring site-wide rules into the admin); typography falls back to browser defaults.
  The starter theme matches closely; other themes may look different on the site than in the canvas.
- **Live data is not shown in the editor**: videos, HTML embeds, posts widgets and dynamic shortcodes appear as
  labelled placeholders (the admin's CSP does not allow third-party frames, and drafts would otherwise leak into
  previews of layout). Use the Preview button to see them.
- **Fixed structure**: sections → columns → widgets; no nested sections, reusable/global sections, templates, custom
  CSS per element, animations or forms (later milestones). Widgets and shortcodes are first-party only until
  plugins (M6).
- **Shortcodes** follow WordPress syntax for self-closing tags only (`[name …]` or `[name … /]`); enclosing pairs such
  as `[x]…[/x]` are not supported, and `[gallery]` takes media ids typed by hand (no picker in the shortcode field;
  the image widget has one).
- **HTML embeds have a fixed height** (set in the widget) because the sandboxed document cannot resize its frame.
- **Keyboard drag and drop** comes from `@dnd-kit`'s keyboard sensor and is not covered by an automated test; the
  move up/down buttons and the navigator are the tested keyboard path.
- **The builder is designed for screens ≥ 1024 px**; it works on tablets and phones (tested at 768 and 375 px) but
  the canvas area is small there.
- **Switching back to rich text** keeps the builder document but shows the old rich-text body; builder content is not
  converted back.
- Some OpenAPI component names are generic (`Schema2`, …) where no title is registered.
- **GitHub CI:** run #21 (commit `689ccca`) passed lint/format/typecheck/build/bundle budget, unit + integration +
  drift + E2E (109 Playwright tests), Node 24, dependency audit and container images (including the fixed admin
  image). The Node 23.7 job failed in `jobs.test.ts › times out hung handlers and retries them` (M3 test code): the
  test app uses a 10 ms retry base, so on a slow runner the retry became due inside the same `drain()` and ran a
  second time (`attempts: 2`). Reproduced locally under CPU load (4 of 4 runs failed), fixed by draining a single
  round, verified under the same load (4 of 4 passed). The product behaviour was correct. Run #22 (commit
  `f3bdf56`) passed all six jobs: lint/format/typecheck/build/bundle budget, unit + integration (with PostgreSQL,
  Valkey and s3mock) + drift + E2E, Node 23.7.0 and 24 compatibility, dependency audit, container images.

### Security considerations for M5
New controls (closed document schema with typed styles, CSS compiled from re-checked values and allowed by hash,
shortcode registry without evaluation, capability-gated HTML embeds in an opaque-origin sandbox) and residual risks
R-23…R-25 are listed in [`docs/security/threat-model.md`](../security/threat-model.md).

## Milestone 6 — Plugins

Plan, scope and decisions: [`docs/milestones/m6-plugins.md`](../milestones/m6-plugins.md). Developer guide:
[`docs/plugins/README.md`](../plugins/README.md).

### Starting point
M5 delivered the visual builder and a fixed set of shortcodes; everything a site could do was compiled into the
application. ADR 0005 had decided that third-party code runs in explicit trust tiers and never in the API process.

### What was built
- **Sandbox** (`packages/plugin-runtime`): plugin code runs in QuickJS compiled to WebAssembly — no Node.js APIs,
  only the `ctx` object built by a small trusted bootstrap — with a fresh runtime and context per call, an engine
  deadline, a stack limit and a hard cap on the WebAssembly memory. Each active plugin has its own child process,
  started with an empty environment and Node's permission model (reads only from the engine's packages; no writes,
  child processes, workers, addons or string code generation). The parent validates every message, kills a child
  that overruns a call, restarts it on demand and marks a plugin as failed after three crashes in ten minutes.
  Prototyping showed why each layer is needed: QuickJS's memory accounting did not stop a ~1.5 GB allocation in
  this build (the WebAssembly cap does, in ~0.1 s), its interrupt is rarely checked inside long native operations
  (the watchdog covers that), and a too-large stack limit crashed the process (now caught as an error).
- **Packages**: a `.zip` with `nexora-plugin.json` and one ES module (plus README/licence), read by a strict ZIP
  reader (central directory only, no encryption/ZIP64/multi-disk, limits before inflating, inflate capped at the
  declared size, CRC checks) and stored in the database. Manifest: id, semantic version, plugin API version,
  permissions and hosts, typed settings, shortcodes with typed attributes, hooks.
- **API** (`modules/extensions`, migration `plugins`, `plugin_storage`, `plugin_logs`, capability `plugins.manage`
  for administrators): install from upload or the bundled `plugins/` folder (inactive), activate (grants exactly the
  manifest's permissions and hosts after loading the code in a throwaway sandbox and checking every declared handler
  is exported; shortcode names must not collide), deactivate, update (stays active only if it asks for nothing new),
  settings (secrets never returned), uninstall, logs — all audited; `PLUGINS_ENABLED` switch.
- **Capabilities** for sandboxed code: private storage (16 KB per value, 1,000 keys, 1 MB), logging, `content:read`
  (published content through the public visibility rules) and `http:fetch` through an **SSRF guard** (approved exact
  hosts, HTTPS on 443, every DNS answer checked against private/reserved ranges, connection pinned to the checked
  address, no redirects, header/size/time limits, 60 requests per minute).
- **Extension points**: plugin shortcodes resolved by the Delivery API (attributes validated against the manifest,
  0.5 s per call, 10 per entry, 2 s per page, 30 s cache; output must be text or allowlisted rich text; themes render
  it without expanding shortcodes inside; inactive plugins' shortcodes stay literal), and `entry.published` /
  `entry.unpublished` events enqueued in the transaction of the change (create, update, trash, restore, scheduled
  publishing) and delivered by the job worker with absolute public URLs, at least once.
- **Admin**: Plugins page (installed, first-party plugins to install/update, upload), permission review that sends
  exactly the permissions shown, plugin page (permissions, shortcodes, generated settings form, recent log, README as
  plain text, deactivate, uninstall); the builder recognises active plugin shortcodes (attributes checked) and shows
  placeholders for them.
- **SDK** (`packages/plugin-sdk`): types, `definePlugin`, packing, and a test harness that runs plugins in the real
  engine with the core's validation and permission rules; `nexora plugin check|pack` and `nexora-plugin`.
- **First-party plugins** (sandboxed like any other): Reading time (`[reading_time]`), Related posts
  (`[related_posts]`, `content:read`), Publish notifications (Slack/Discord on publish, `http:fetch` to those hosts).
- **Fixes found on the way**: Node's `BlockList` matches IPv4 addresses against IPv6 rules, so the `::ffff:0:0/96`
  rule refused every public IPv4 address — found by a unit test, fixed with one list per family; the edge nginx
  limited request bodies to 1 MB, below the 2 MB package limit — a location for `/api/v1/plugins` was added; the
  plugin settings form remounted when the plugin changed, losing input (found by E2E); Vitest's shared module cache
  could be cleared by one process while another used it — one cache per package now.

### Known limitations and caveats (honest list)

- **Sandbox strength:** an escape would need bugs in both QuickJS and V8's WebAssembly sandbox; the child would then
  have no secrets, database access or writable files, but **could open network connections** (Node's permission
  model in the supported versions does not cover the network). Restrict egress at the network level where that
  matters (R-26).
- **What plugins can do is deliberately small:** shortcodes and two events; no admin pages of their own, builder
  widgets, routes, write access to content, scheduled tasks, or access to users and settings. No marketplace,
  signatures or automatic updates. No trusted in-process plugins.
- **Within its grants a plugin decides what its shortcodes show** (allowlisted text and links) and what it sends to
  approved hosts (public content, its own settings) (R-27).
- **Performance:** each plugin shortcode call costs a round trip to the plugin's process (results cached 30 s per
  API process); an active plugin keeps a process of a few tens of MB while in use (stopped after 10 minutes idle);
  limits apply per API/worker process (rate limits are per process) (R-28).
- **Secrets in plugin settings** are stored unencrypted in the database (never returned by the API) (R-29).
- **Plugin code must be one bundled ES module** without imports, timers or browser/Node APIs; QuickJS lacks some
  web APIs (e.g. `URL`), which authors must replace.
- **Hierarchical content** (child pages) is not returned by `content:read` (their ancestors would need checking).
- The admin's initial bundle is at 214.6 of 215 kB; the next additions to the shell need trimming elsewhere.

R-26…R-29; R-02 (trusted plugins) no longer applies.
