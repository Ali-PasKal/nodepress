# Milestone 3 — Content, media and background jobs

## Starting point
M2 delivered identity, sessions, capability-based authorisation, the setup wizard and the audit log.
Mail is sent in-process with development transports only, expired sessions and reset tokens are never
purged, and the Editor, Author, Contributor and Viewer roles can only sign in.

## Scope

**In scope**
- **Durable job queue** in PostgreSQL: jobs are enqueued in the same transaction as the change that needs
  them (outbox semantics), claimed with `FOR UPDATE SKIP LOCKED`, retried with exponential backoff, and
  moved to a `dead` state after the last attempt. `LISTEN/NOTIFY` wakes workers; polling is the fallback.
  Abandoned jobs (worker crash) are reclaimed after a lock timeout. Recurring tasks are deduplicated across
  workers. The worker runs embedded in the API by default or as a separate process (`dist/worker.js`).
- **Mail**: SMTP transport (TLS required in production); password reset emails are produced by a job, so a
  crash cannot lose them and the reset token is still never stored in plain text.
- **Maintenance jobs**: purge expired sessions, reset tokens, rate-limit buckets, finished jobs and trashed
  content past its retention; publish scheduled content every minute.
- **Content model**: content types (built-in Post and Page, plus custom types with custom fields),
  taxonomies (built-in Category and Tag, plus custom ones) and terms, entries with statuses `draft`,
  `pending` (submitted for review), `scheduled`, `published`, a separate trash state, hierarchical pages
  with unique paths, slugs, excerpts, featured images, a structured rich-text body, optimistic concurrency,
  revisions with restore, and bulk actions.
- **Content capabilities** and their mapping to the built-in roles, with ownership rules (own vs. others',
  editing published content, publishing) enforced in one policy service.
- **Media library**: uploads validated by content sniffing (not file names or client MIME types), image
  re-encoding that strips metadata (EXIF/GPS) and auto-orients, responsive variants generated by a job,
  alt text and captions, safe serving (`/uploads/...`, correct types, `nosniff`, range requests), and a
  storage abstraction with local-disk and S3-compatible drivers.
- **Admin**: content lists (filters, search, pagination, bulk actions), an editor (rich text, status and
  scheduling, slug, excerpt, featured image, taxonomies, custom fields, parent page, revisions, unsaved
  changes and conflict handling), term management, a content type and field builder, the media library and
  picker, a background jobs page, and a command palette.

**Out of scope (later milestones, stated honestly in the UI and docs)**
- Public rendering of content, the Delivery API, menus and SEO metadata (M4). M3 content is managed and
  stored, not yet shown on a public site; "View" links appear in M4.
- The visual page builder (M5). Pages use the same structured rich-text body as posts until then.
- Per-content-type capabilities, editorial comments, autosave, content locking, localisation.
- Full-text search (admin search uses case-insensitive matching on title, excerpt and body text).
- Video transcoding, SVG uploads (rejected: SVG can carry scripts), image cropping/focal points.

## Key decisions
| Decision | Rationale |
|---|---|
| Queue in PostgreSQL, not Redis | Transactional enqueue (no lost or phantom jobs), one fewer required service; Redis stays optional |
| At-least-once execution; handlers must be idempotent | The only guarantee a crash-safe queue can give honestly |
| Password reset job creates the token at send time | Keeps "only hashes at rest": job payloads never contain the token |
| Rich text stored as a ProseMirror/TipTap JSON document, validated against a strict allowlist schema on the server | No HTML is stored, so stored XSS through content is impossible by construction; renderers (M4) escape text and only emit allowlisted nodes, marks and URL schemes |
| Hierarchical uniqueness via a stored `path` (`about/team`) unique per site and type | Lets sibling pages under different parents share slugs and gives the M4 router a direct lookup key |
| Trash is a separate flag (`trashed_at`), not a status | Restoring returns an entry to exactly the status it had |
| Optimistic concurrency with a `version` column | Two editors cannot silently overwrite each other (409 with the current version) |
| Uploads accepted only for sniffed types: JPEG, PNG, GIF, WebP, AVIF, PDF, MP4, WebM, MP3, OGG, WAV | Extensions and client MIME types are attacker-controlled; SVG and HTML are excluded |
| Media URLs contain a random id and are immutable | Long-lived caching (`immutable`) is safe; deleting a file removes it everywhere |
| Generic content capabilities, not per type | Matches the built-in roles; per-type rules can be layered on later without changing stored data |

## Risks
- Duplicate or lost jobs → transactional enqueue, `SKIP LOCKED`, lock ownership checks on completion, tests
  that kill a worker mid-job and race two workers.
- Stored XSS through rich text, link URLs or image sources → allowlist schema with tests for hostile input.
- Malicious uploads (polyglots, decompression bombs, path traversal) → content sniffing, pixel limits,
  re-encoding, server-generated storage keys, strict key validation when serving.
- Privilege bugs in the own/others matrix → one policy service, table-driven tests for every role.
- Lost updates between editors → version checks, tested.
- Upload memory pressure → size limit (25 MB default), one file per request, per-user upload rate limit.

## Acceptance criteria
1. Jobs enqueued inside a rolled-back transaction never run; committed jobs run exactly once under normal
   operation even with two workers; failures retry with backoff and end in `dead` after the last attempt;
   a job whose worker died is reclaimed after the lock timeout; recurring tasks run once per slot.
2. The worker runs embedded or as a separate process and shuts down gracefully (no new claims, running jobs
   finish or are released).
3. Password reset email is delivered through a job over real SMTP (test server); the job payload contains no
   token; SMTP without TLS is refused in production configuration.
4. Maintenance purges expired sessions, reset tokens, rate-limit buckets, finished jobs and expired trash;
   scheduled entries are published when due, with audit events.
5. Content types, taxonomies and terms can be created, edited and deleted with validation; built-in types and
   taxonomies cannot be deleted; types with entries cannot be deleted.
6. Entries support create, edit, status transitions, scheduling, trash/restore/permanent delete and bulk
   actions; custom field values are validated against the type's field definitions; slugs and paths are
   unique per type (siblings may share slugs in hierarchical types); a parent cannot be an entry's own
   descendant.
7. Concurrent edits are detected (409); every save creates a revision; revisions can be listed, viewed and
   restored; revision retention is bounded.
8. The ownership/capability matrix holds for every built-in role (automated, table-driven tests), including
   contributors not publishing or editing published content, authors not touching others' content, and
   viewers being read-only.
9. Rich text that contains disallowed nodes, marks, attributes or URL schemes (e.g. `javascript:`) is rejected.
10. Uploads: only sniffed allowlisted types are accepted regardless of name or declared type; images are
    re-encoded without metadata and get variants via a job; size and pixel limits are enforced; files are
    served with the right type, `nosniff`, immutable caching and range support; traversal attempts fail.
    The local driver is tested, and the S3 driver is tested against an S3-compatible server.
11. Admin UI: content lists, editor (rich text, scheduling, revisions, featured image, terms, fields, parent),
    terms, content types and fields, media library and picker, jobs page and command palette work against
    the real API with loading/empty/error states, keyboard access, and responsive layouts at 375/768/1280.
12. All checks (lint, format, typecheck, build, bundle budget, unit/integration, E2E, drift, audit) pass on
    Node 22 and Node 23.7; the Compose stack runs with a separate worker; CI green.
